| ID | Description | File & line no. | Type | Severity | Confidence | Proposed action |

| 1 | The package-level API description says the module exposes a curated public surface, but the root package does not define `__all__` and instead star-imports implementation modules (`from .time_utils import *`, `from .timewindow import *`, `from .timeperiods import *`, `from .time_parsing import *`). This leaks non-public implementation details such as `datetime`, `warnings`, `typing`, `sys`, and `UNIT_CONVERSIONS` into `d3tools.timestepping` and into the generated reference page for `::: d3tools.timestepping`. That makes the reference page broader than the intended public API and can mislead callers about what is supported. | [src/d3tools/timestepping/__init__.py](src/d3tools/timestepping/__init__.py#L1-L41), [docs/developer/reference/timestepping.md](docs/developer/reference/timestepping.md#L1-L23) | Documentation mismatch | medium | confirmed | Define an explicit `__all__` for the root package and restrict the page to the intended public API, or clearly document the legacy compatibility aliases that are intentionally exposed. |
| 2 | The public contract is unclear because the subpackage `timeperiods` declares `__all__`, while the root package does not. The result is an inconsistent API boundary: callers can import names from `d3tools.timestepping` that are not part of the documented time-step surface, while the subpackage advertises a tightly curated export list. This is a docs/API-contract gap rather than a failing runtime bug, but it matters to users and to generated reference content. | [src/d3tools/timestepping/__init__.py](src/d3tools/timestepping/__init__.py#L12-L41), [src/d3tools/timestepping/timeperiods/__init__.py](src/d3tools/timestepping/timeperiods/__init__.py#L1-L18) | Unclear API contract | medium | confirmed | Align the root export policy with the subpackage policy by declaring a root `__all__` and documenting which compatibility aliases remain intentionally public. |
